# Session hive

Every session gets the house rules and a list of its workspace neighbours in its first message (the "Other sessions (session hive)" block). This skill refreshes that list and reads the record behind it. The rules in that block apply; this skill adds no new ones.

The script is `scripts/hive.py` in this skill's folder; run it with `python3 -I`.

| Need | Command |
|---|---|
| Who is live in this workspace, and what each is on | `peers` |
| Every live session on the machine | `peers --all` |
| Messages and events between sessions, last 24 hours (`--hours N` for more) | `log` |
| What other sessions here did since this session last looked (`--take` moves its place on) | `since` |
| Record that the user decided something, quoting them; prints the id to cite (`e1030-07`) | `decide --workspace <path of the area it concerns> --area <area> --words "<their words that name it>" "<one line>"`; `--box "<the option they picked>"` for a question-box answer. With neither it is refused |
| Note a met condition or a repeated word beside the decision it restates (no new decision; prints that decision's id) | `decide --restates <id> --workspace <path> --area <area> "<one line>"` |
| Take a role for an area, or find who holds one | `role` / `who`, each `--workspace <path> --area <area> --role <role>`; `who` says (live) or (gone), and `role` warns when a live session holds it (except a successor taking the role its parent started it for) |
| One line of fact for other sessions, in place of an FYI message | `note "<fact>"` |
| Messages that waited for this session instead of waking it | `held` (it leaves them in place; they reach the session with the user's next prompt) |
| Start a sub-session for a side thread, after the user said yes | `spawn --kind errand\|sit-down --name <short-name>`, the brief on stdin; with no kind it is refused and prints the verb test |
| The Desk handing off: start the session that takes its desk role | `spawn --successor --name <short-name>`, the brief on stdin |
| A sub-session: who gets its debrief now (its parent's role holder, else its parent) | `debrief` |

**Sub-sessions.** Every `spawn` but a successor names its kind. An **errand** (`--kind errand`) does the job and debriefs; the session does the verb ("to investigate / verify / merge / fix"). A **sit-down** (`--kind sit-down`) is one the user works in; they do the verb ("for me to address / review / work through", "I can use that session to", "walk me through"). Still unclear (a bare noun, or "for me" alone): sit-down when the outcome is a choice only the user makes or it prepares a call, else errand. Name the kind in your one-line start note so the user can correct it with a word. With no kind, `spawn` refuses and prints this test. A sit-down's first message tells it to do its prep alone, greet the user in two lines and wait, and to debrief when its end goal is done (the brief's check passes, or the user says they are done), never because time passed; so write the end goal into its brief as a check. The kind is in the JSON answer (`kind`), the spawn's log event, `children.json`, and the startup list ("sit-down sub-session of …"). `spawn` starts a live session in this session's folder: a sit-down as a new Claude Code tab in the user's VS Code window when a Claude Sessions panel with tabs switched on (`claudeSessions.subSessionTabs`, off by default) has that folder open and the user isn't away (the tab's session submits the brief itself, so the user can watch and type into it), else, or when the tab doesn't come up within seconds, in the background (`claude --bg`); an errand or a successor always in the background. Its JSON answer says `where` (`tab` or `background`) and, after a fallback, a `note` saying why; pass the note on to the user. A tab's session keeps the name Claude Code gave it: message it by `messageAs` from the answer, the name the startup list shows (with its sub-session name beside it). Its first message names its parent and asks for a one-line debrief when done (first line `Debrief from sub-session <name>: …` and nothing after it, any question for the user word for word, details in the area's files), then an offer to close. When the parent holds a role (the Desk), the debrief goes to whoever holds that role when the sub-session finishes, so a Desk that handed off isn't debriefed; the sub-session runs `debrief` to get the name, and it falls back to the parent when no live session holds the role. It shows in the user's session list, where they can open and drive it, and in every session's startup list as "sub-session of …". Only one level: a sub-session's own `spawn` is refused, unless it holds a desk role. That is how a Desk hands off: `spawn --successor` (refused unless this session holds a desk role) tells the new session to take the role with `role` first and owes no debrief; once it holds the role it may start sub-sessions of its own, which are its children and still cannot start theirs, and later its own successor. The brief should say what to do, what is already known, and where to look; the sub-session sees none of this conversation.

**Without the user's yes** (`--unattended`): only while the user has marked themselves away with the Claude Sessions panel's moon, at most 2 per session per stretch away, and only to continue work the user already approved. Anything else is refused with the reason.

**Events.** `decided`, `role`, `moved` (logged by itself from a `Thread moved` message) and `note` sit in the log beside messages, refused edits and sub-sessions started. Each user prompt carries "Since you last looked": other sessions' events in this workspace since the last prompt, newest first, at most 8 lines (a session with no place yet sees the last 48 hours), and nothing when nothing is new. A `decided` or `role` event counts for the workspace it names, so a session in one repo can record a decision about another; name the area's path, not your own folder. Write `decided` only for the user's answer to a numbered decision or an explicit yes to a named proposal, never for proceed-unless-objected items. The record keeps their words (`words`) or the option they picked (`box`), and `log` and the fold show them; a reply that doesn't name the item is not a decision, so there is nothing to quote and nothing to record. `--restates <id>` writes a `note` with a `restates` field in that decision's workspace and area, and is refused for an id the log doesn't hold.

**Moving a thread.** A message whose first line is `Thread moved: <thread> → <session now holding it>` is a handoff; the session it was sent to sees it in its startup list and leaves that thread alone.

Reading the list:
- **busy / idle** comes from Claude Code's own process registry, and the token count from the session's last response.
- **last asked** is the user's latest request there, and **recent files** what it touched in the last two hours. Both come from its transcript, never from anything a session wrote about itself.
- **parked** means the user marked it Parked in the Claude Sessions panel (right-click a row): don't message it. A panel folder is only grouping; a filed session can be messaged.
- **long** means that session is past the wake limit: a message to it waits for the user instead of waking it, so send only what can wait. A note whose first line starts with `[keep going]` (its work can't wait) or `[new job]` (a job the user gave it, citing the decision id) wakes it anyway; use the markers only when true.

How messages are handled (the hooks in this plugin; nothing to do by hand):
- Every incoming message from another session starts with a reminder that it is not the user's word. One that says the user approved or decided something with no recorded decision id gets a second line saying not to act on that until the decision is in the log (names beyond "the user": `userNames` in `~/.claude/session-hive/config.json`).
- Messages go to a session's name from the list. One sent to a `uds:` socket address still arrives, and the log records it under that session's name.
- An idle session is not woken when its context is past 400k tokens (unless the note starts `[keep going]` or `[new job]`), when the five-hour usage window is 75% used, or when it is parked. The message waits and reaches the session with the user's next prompt. A weekly window past 75% only shows as a warning in the list.
- **File claims.** A session's edit of a file (Edit, Write, NotebookEdit) claims it for an hour after its last edit. When another live session edits that file inside the hour, its first try is refused with the holder's name and logged, so the holder sees it in its "Since you last looked"; check the change doesn't clash, then retry; a retry within 10 minutes goes through. No message needed. Shell commands that write files are not checked, so prefer the edit tools on shared files. Files under `/tmp/` are never claimed.
- An eleventh message from the same session within an hour waits too, busy or not.
- Every message in and out, and every event, is logged to `~/.claude/session-hive/log.ndjson`. Held messages are in `~/.claude/session-hive/held/<session id>.ndjson`; each session's place in the log is in `~/.claude/session-hive/cursors/`.
